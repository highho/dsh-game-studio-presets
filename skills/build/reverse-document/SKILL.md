# 反向文档

此skill分析现有实现（代码、原型、系统）并生成
适当的设计或架构文档。在以下情况使用：
- 您在没有先编写设计文档的情况下构建了功能
- 您继承了没有文档的代码库
- 您原型化了机制并需要将其正式化
- 您需要记录现有代码背后的"为什么"

---

## 工作流

### 1. 解析参数

**格式**: `/reverse-document <type> <path>`

**类型选项**：
- `design` → 生成游戏设计文档（GDD章节）
- `architecture` → 生成架构决策记录（ADR）
- `concept` → 从原型生成概念文档

**路径**: 要分析的目录或文件
- `src/gameplay/combat/` → 所有战斗相关代码
- `src/core/event-system.cpp` → 特定文件
- `prototypes/stealth-mech/` → 原型目录

**示例**：
```bash
/reverse-document design src/gameplay/magic-system
/reverse-document architecture src/core/entity-component
/reverse-document concept prototypes/vehicle-combat
```

### 2. 分析实现

**读取并理解代码/原型**：

**对于设计文档（GDD）：**
- 识别机制、规则、公式
- 提取游戏值（伤害、冷却、范围）
- 查找状态机、能力系统、进度
- 检测代码中处理的边缘情况
- 映射依赖关系（什么系统交互？）

**对于架构文档（ADR）：**
- 识别模式（ECS、单例、观察者等）
- 理解技术决策（线程、序列化等）
- 映射依赖关系和耦合
- 评估性能特征
- 查找约束和权衡

**对于概念文档（原型分析）：**
- 识别核心机制
- 提取涌现的游戏模式
- 记录什么有效 vs 什么无效
- 查找技术可行性见解
- 记录玩家幻想 / 手感

### 3. 询问澄清问题（协作协议）

**不要**只描述代码。**询问**意图：

**设计问题**：
- "我看到一个在战斗中消耗的耐力系统。这是为了：
  - 节奏（防止垃圾）？
  - 资源管理（战略深度）？
  - 还是其他？"
- "踉跄机制似乎是核心。这是核心支柱还是支持功能？"
- "伤害随等级指数增长。是有意的力量幻想，还是需要重新平衡？"

**架构问题**：
- "您正在使用服务定位器模式。这是为了选择：
  - 可测试性（模拟依赖）？
  - 解耦（减少硬引用）？
  - 还是从现有代码继承的？"
- "我看到手动内存管理而不是智能指针。性能要求，还是遗留？"

**概念问题**：
- "原型强调潜行而非战斗。这是预期的支柱吗？"
- "玩家似乎利用抓钩来加速。是功能还是错误？"

### 4. 呈现发现

起草前，显示您发现的内容：

```
我已分析 src/gameplay/combat/。这是我发现的：

已实现的机制：
- 3连击系统带时机窗口
- 破防机制（重攻击 vs 格挡敌人）
- 耐力系统（攻击/闪避时消耗，空闲时恢复）
- 踉跄系统（累积，触发脆弱状态）

发现的公式：
- 伤害 = 基础 * (1 + 力量缩放 * 等级)
- 踉跄累积 = 攻击踉跄值 / (敌人.韧性 * 0.5)
- 耐力消耗 = 基础耐力消耗 * (1 - 效率加成)

意图不清楚的区域：
1. 耐力系统——节奏还是资源管理？
2. 踉跄——核心支柱还是支持功能？
3. 伤害缩放——力量幻想还是需要调整？

在我起草设计文档之前，您能澄清这些点吗？
```

等待用户澄清意图后再起草。

### 5. 使用模板起草文档

基于类型，使用适当的模板：

| 类型 | 模板 | 输出路径 |
|------|----------|-------------|
| `design` | `templates/design-doc-from-implementation.md` | `design/gdd/[system-name].md` |
| `architecture` | `templates/architecture-doc-from-code.md` | `docs/architecture/[decision-name].md` |
| `concept` | `templates/concept-doc-from-prototype.md` | `prototypes/[name]/CONCEPT.md` 或 `design/concepts/[name].md` |

**草稿结构**：
- 捕获**存在什么**（机制、模式、实现）
- 记录**为什么存在**（与用户澄清的意图）
- 识别**缺失什么**（未处理的边缘情况、设计差距）
- 标记**后续工作**（平衡调整、缺失功能）

### 6. 显示草稿并请求批准

**协作协议**：
```
我已根据您的代码和澄清起草了战斗系统设计文档。

[显示关键章节：概述、机制、公式、设计意图]

我做的补充：
- 根据您的澄清将耐力记录为"节奏机制"
- 添加了代码中没有的边缘情况（如果耐力在连击中归零会怎样？）
- 标记了平衡关注：高等级时的指数伤害缩放

标记为不完整的章节：
- "敌人AI与踉跄的交互"（尚未完全实现）
- "武器多样性和缩放"（目前只实现了剑）

我可以将此写入 design/gdd/combat-system.md 吗？
```

等待批准。用户可能在写入前请求更改。

### 7. 用元数据写入文档

批准后，用特殊标记写入文件：

```markdown
---
status: reverse-documented
source: src/gameplay/combat/
date: 2026-02-13
verified-by: [用户姓名]
---

# 战斗系统设计

> **注意**: 本文档是从现有实现反向工程而来的。
> 它捕获当前行为和澄清的设计意图。某些章节可能是
> 不完整的，因为实现是部分的或意图不清楚。

[文档其余部分...]
```

### 8. 标记后续工作

写入后，建议下一步：

```
✅ 已写入 design/gdd/combat-system.md

建议后续：
1. 对战斗公式运行 /balance-check（指数缩放关注）
2. 为耐力系统架构决策创建ADR
3. 实现缺失的边缘情况：
   - 连击中耐力耗尽行为
   - 闪避期间的踉跄状态
4. 实现武器多样性时扩展设计文档

您想现在处理这些吗？
```

## 模板选择逻辑

| 如果分析... | 使用模板... | 因为... |
|----------------|-----------------|------------|
| `src/gameplay/*` | design-doc-from-implementation.md | 游戏玩法机制 → GDD |
| `src/core/*`, `src/ai/*` | architecture-doc-from-code.md | 核心系统 → ADR |
| `prototypes/*` | concept-doc-from-prototype.md | 实验 → 概念文档 |
| `src/networking/*` | architecture-doc-from-code.md | 技术系统 → ADR |
| `src/ui/*` | design-doc-from-implementation.md | UI/UX → 设计规格 |

## 协作协议

此skill遵循协作设计原则：

1. **先分析**: 读取代码，理解实现
2. **询问意图**: 询问"为什么"，不只是"什么"
3. **呈现发现**: 显示发现，突出不清楚的区域
4. **用户澄清**: 将意图与意外分开
5. **起草文档**: 基于现实 + 意图创建文档
6. **显示草稿**: 显示关键章节，解释补充
7. **获取批准**: "我可以写入 [filepath] 吗？"
8. **标记后续**: 建议相关工作，不要自动执行

**绝不假设意图。在记录"为什么"之前始终询问。**
