description: "快速原型工作流。跳过正常标准以快速验证游戏概念或机制。产生一次性代码和结构化原型报告。"
argument-hint: "[concept-description]"
user-invocable: true
allowed-tools: Read, Glob, Grep, Write, Edit, Bash
---

当此skill被调用时：

1. **从参数读取概念描述**。识别此原型必须回答的
   核心问题。如果概念模糊，在继续之前明确说明
   问题。

2. **读取CLAUDE.md** 获取项目上下文和当前技术栈。理解
   使用什么引擎、语言和框架，以便原型使用兼容的工具构建。

3. **创建原型计划**: 用3-5个项目符号定义最小
   可行原型的样子。核心问题是什么？回答它所需的绝对
   最小代码是什么？什么可以跳过？

4. **创建原型目录**: `prototypes/[concept-name]/` 其中
   `[concept-name]` 是从概念派生的短kebab-case标识符。

5. **在隔离目录中实现原型**。每个文件必须以以下内容开头：
   ```
   // 原型 - 不用于生产
   // 问题: [正在测试的核心问题]
   // 日期: [当前日期]
   ```
   标准被有意放宽：
   - 自由硬编码值
   - 使用占位资源
   - 跳过错误处理
   - 使用最简单的有效方法
   - 复制代码而不是从生产导入

6. **测试概念**: 运行原型。观察行为。收集任何
   可测量数据（帧时间、交互计数、手感评估）。

7. **生成原型报告**并保存到
   `prototypes/[concept-name]/REPORT.md`：

```markdown
## 原型报告: [概念名称]

### 假设
[我们期望为真——我们着手回答的问题]

### 方法
[我们构建了什么、花了多长时间、我们采取了什么捷径]

### 结果
[实际发生了什么——具体观察，不是意见]

### 指标
[测试期间收集的任何可测量数据]
- 帧时间: [如果相关]
- 手感评估: [主观但具体——"200ms延迟时响应感觉迟钝"而不是"感觉不好"]
- 玩家行动计数: [如果相关]
- 迭代计数: [多少次尝试才让它工作]

### 建议: [继续 / 转向 / 放弃]

[用证据解释建议的一个段落]

### 如果继续
[生产质量实现需要改变什么]
- 架构要求
- 性能目标
- 对原始设计的范围调整
- 估算生产工作量

### 如果转向
[结果建议的替代方向]

### 如果放弃
[为什么这个概念不起作用以及我们应该做什么]

### 经验教训
[影响其他系统或未来工作的发现]
```

8. **向用户输出摘要**：核心问题、结果和
   建议。链接到 `prototypes/[concept-name]/REPORT.md` 的完整报告。

### 重要约束

- 原型代码绝不能从生产源文件导入
- 生产代码绝不能从原型目录导入
- 如果建议是继续，生产实现必须
  从头开始编写——原型代码不会重构到生产中
- 总原型工作量应该被时间限制为1-3天等效工作
- 如果原型范围开始增长，停止并重新评估
  问题是否可以简化
