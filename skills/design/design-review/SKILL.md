当此skill被调用时：

1. **完整读取目标设计文档**。

2. **读取主CLAUDE.md**以了解项目上下文和标准。

3. **读取相关设计文档**，被目标文档引用或暗示的
   （检查`design/gdd/`中的相关系统）。

4. **根据设计文档标准清单评估**：
   - [ ] 有概述部分（一段摘要）
   - [ ] 有玩家幻想部分（预期感觉）
   - [ ] 有详细规则部分（明确的机制）
   - [ ] 有公式部分（所有数学定义及变量）
   - [ ] 有边缘情况部分（处理的异常情况）
   - [ ] 有依赖关系部分（列出的其他系统）
   - [ ] 有调整旋钮部分（识别的可配置值）
   - [ ] 有验收标准部分（可测试的成功条件）

5. **检查内部一致性**：
   - 公式产生的值是否与描述的行为匹配？
   - 边缘情况是否与主要规则矛盾？
   - 依赖关系是否是双向的（另一个系统知道这一个吗）？

6. **检查可实现性**：
   - 规则是否足够精确，程序员可以在不猜测的情况下实现？
   - 是否有任何"含糊"部分缺少细节？
   - 是否考虑了性能影响？

7. **检查跨系统一致性**：
   - 这是否与任何现有机制冲突？
   - 这是否与其他系统产生意外交互？
   - 这是否与游戏既定的基调和支柱一致？

8. **以此格式输出审查**：

```markdown
## 设计审查: [文档标题]

### 完整性: [X/8 部分存在]
[列出缺失的部分]

### 一致性问题
[列出任何内部或跨系统矛盾]

### 可实现性问题
[列出任何模糊或无法实现的部分]

### 平衡问题
[列出任何明显的平衡风险]

### 建议
[优先改进列表]

### 裁决: [批准 / 需要修订 / 需要重大修订]
```

9. **上下文下一步建议**：
   - 如果被审查的文档是`game-concept.md`或`game-pillars.md`：
     - 检查`design/gdd/systems-index.md`是否存在
     - 如果不存在，添加到建议：
       > "此概念已准备好进行系统分解。运行`/map-systems`
       > 将其分解为具有依赖关系和优先级的单个系统，
       > 然后编写每个系统的GDD。"
   - 如果文档是单个系统GDD：
     - 检查系统索引是否引用此系统
     - 如果裁决是批准：建议"更新系统索引中此系统的
       状态为'已批准'。"
     - 如果裁决是需要修订或需要重大修订：建议"更新
       系统索引中此系统的状态为'审查中'。"
     - 注意：此skill是只读的。用户（或`/design-system`）必须
       在系统索引中执行实际状态更新。
