# 阶段门验证

此skill验证项目是否准备好进入下一个开发
阶段。它检查必需的产物、质量标准和阻塞项。

**与 `/project-stage-detect` 的区别**: 该skill是诊断性的（"我们在哪里？"）。
此skill是规定性的（"我们准备好推进了吗？"带有正式裁决）。

## 生产阶段 (7)

项目通过这些阶段推进：

1. **概念** — 头脑风暴、游戏概念文档
2. **系统设计** — 映射系统、编写GDD
3. **技术设置** — 引擎配置、架构决策
4. **预生产** — 原型设计、垂直切片验证
5. **生产** — 功能开发（Epic/Feature/Task 追踪激活）
6. **打磨** — 性能、游戏测试、错误修复
7. **发布** — 发布准备、认证

**当门通过时**，将新阶段名称写入 `production/stage.txt`
（单行，例如 `Production`）。这会立即更新状态行。

---

## 1. 解析参数

- **带参数**: `/gate-check production` — 验证该特定阶段的准备情况
- **无参数**: 使用与
  `/project-stage-detect` 相同的启发式方法自动检测当前阶段，然后验证下一个阶段转换

---

## 2. 阶段门定义

### 门: 概念 → 系统设计

**必需产物：**
- [ ] `design/gdd/game-concept.md` 存在并有内容
- [ ] 游戏支柱已定义（在概念文档或 `design/gdd/game-pillars.md` 中）

**质量检查：**
- [ ] 游戏概念已审查（`/design-review` 裁决不是需要重大修订）
- [ ] 核心循环已描述并被理解
- [ ] 目标受众已确定

---

### 门: 系统设计 → 技术设置

**必需产物：**
- [ ] 系统索引存在于 `design/gdd/systems-index.md`，至少有MVP系统枚举
- [ ] `design/gdd/` 中至少有1个GDD（除了game-concept.md和systems-index.md）

**质量检查：**
- [ ] GDD通过设计审查（8个必需章节存在）
- [ ] 系统依赖关系在系统索引中映射
- [ ] MVP优先级层级已定义

---

### 门: 技术设置 → 预生产

**必需产物：**
- [ ] 引擎已选择（CLAUDE.md 技术栈不是 `[CHOOSE]`）
- [ ] 技术偏好已配置（`.claude/docs/technical-preferences.md` 已填充）
- [ ] `docs/architecture/` 中至少有1个架构决策记录
- [ ] `docs/engine-reference/` 中存在引擎参考文档

**质量检查：**
- [ ] 架构决策涵盖核心系统（渲染、输入、状态管理）
- [ ] 技术偏好已设置命名约定和性能预算

---

### 门: 预生产 → 生产

**必需产物：**
- [ ] `prototypes/` 中至少有1个原型带有README
- [ ] `production/sprints/` 中存在第一个冲刺计划
- [ ] 系统索引中的所有MVP层级GDD都已完成

**质量检查：**
- [ ] 原型验证核心循环假设
- [ ] 冲刺计划引用GDD中的实际工作项
- [ ] 垂直切片范围已定义

---

### 门: 生产 → 打磨

**必需产物：**
- [ ] `src/` 有按子系统组织的活动代码
- [ ] GDD中的所有核心机制都已实现（将 `design/gdd/` 与 `src/` 交叉引用）
- [ ] 主要游戏路径可从头到尾玩
- [ ] `tests/` 中存在测试文件
- [ ] 至少有1份游戏测试报告（或已运行 `/playtest-report`）

**质量检查：**
- [ ] 测试通过（通过Bash运行测试套件）
- [ ] 任何错误追踪器或已知问题中没有严重/阻塞性错误
- [ ] 核心循环按设计玩（与GDD验收标准比较）
- [ ] 性能在预算内（检查technical-preferences.md目标）

---

### 门: 打磨 → 发布

**必需产物：**
- [ ] 里程碑计划中的所有功能都已实现
- [ ] 内容完整（设计文档中引用的所有关卡、资源、对话都存在）
- [ ] 本地化字符串已外部化（`src/` 中没有硬编码的面向玩家的文本）
- [ ] QA测试计划存在
- [ ] 平衡数据已审查（已运行 `/balance-check`）
- [ ] 发布检查清单已完成（已运行 `/release-checklist` 或 `/launch-checklist`）
- [ ] 商店元数据已准备（如果适用）
- [ ] 变更日志 / 补丁说明已起草

**质量检查：**
- [ ] 完整QA通过由 `qa-lead` 签署
- [ ] 所有测试通过
- [ ] 所有目标平台的性能目标达成
- [ ] 没有已知的严重、高或中等严重性错误
- [ ] 涵盖基本无障碍功能（重新映射、文本缩放（如果适用））
- [ ] 所有目标语言的本地化已验证
- [ ] 满足法律要求（EULA、隐私政策、年龄评级（如果适用））
- [ ] 构建干净地编译和打包

---

## 3. 运行门检查

对于目标门中的每个项目：

### 产物检查
- 使用 `Glob` 和 `Read` 验证文件存在并有有意义的内容
- 不要只检查存在性——验证文件有实际内容（不仅仅是模板标题）
- 对于代码检查，验证目录结构和文件计数

### 质量检查
- 对于测试检查：如果配置了测试运行器，通过 `Bash` 运行测试套件
- 对于设计审查检查：`Read` GDD并检查8个必需章节
- 对于性能检查：`Read` technical-preferences.md并与任何
  `tests/performance/` 中的分析数据或最近的 `/perf-profile` 输出比较
- 对于本地化检查：`Grep` `src/` 中的硬编码字符串

### 交叉引用检查
- 将 `design/gdd/` 文档与 `src/` 实现比较
- 检查架构文档中引用的每个系统都有相应的代码
- 验证冲刺计划引用实际工作项

---

## 4. 协作评估

对于无法自动验证的项目，**询问用户**：

- "我无法自动验证核心循环是否玩得好。它已经被游戏测试过了吗？"
- "未找到游戏测试报告。是否进行了非正式测试？"
- "性能分析数据不可用。您想运行 `/perf-profile` 吗？"

**绝不假设未验证项目的通过。** 将它们标记为需要手动检查。

## 5. 输出裁决

```
## 门检查: [当前阶段] → [目标阶段]

**日期**: [日期]
**检查者**: gate-check skill

### 必需产物: [X/Y 存在]
- [x] design/gdd/game-concept.md — 存在, 2.4KB
- [ ] docs/architecture/ — 缺失（未找到ADR）
- [x] production/sprints/ — 存在, 1个冲刺计划

### 质量检查: [X/Y 通过]
- [x] GDD有8/8必需章节
- [ ] 测试 — 失败（tests/unit/中有3个失败）
- [?] 核心循环已游戏测试 — 需要手动检查

### 阻塞项
1. **没有架构决策记录** — 在进入生产之前运行 `/architecture-decision` 创建一个
   涵盖核心系统架构。
2. **3个测试失败** — 在推进之前修复 tests/unit/ 中的失败测试。

### 建议
- [解决阻塞项的优先行动]
- [不是阻塞性的可选改进]

### 裁决: [通过 / 关注 / 失败]
- **通过**: 所有必需产物存在，所有质量检查通过
- **关注**: 存在小差距但可以在下一阶段解决
- **失败**: 必须在推进之前解决关键阻塞项
```

---

## 6. 通过时更新阶段

当裁决是**通过**且用户确认他们想要推进时：

1. 将新阶段名称写入 `production/stage.txt`（单行，无尾随换行符）
2. 这会立即更新所有未来会话的状态行

示例：如果通过"预生产 → 生产"门：
```bash
echo -n "Production" > production/stage.txt
```

**写入前始终询问**: "门通过。我可以将 `production/stage.txt` 更新为 'Production' 吗？"

---

## 7. 后续行动

基于裁决，建议具体的下一步：

- **没有游戏概念？** → `/brainstorm` 创建一个
- **没有系统索引？** → `/map-systems` 将概念分解为系统
- **缺少设计文档？** → `/reverse-document` 或委派给 `game-designer`
- **缺少ADR？** → `/architecture-decision`
- **测试失败？** → 委派给 `lead-programmer` 或 `qa-tester`
- **没有游戏测试数据？** → `/playtest-report`
- **性能未知？** → `/perf-profile`
- **未本地化？** → `/localize`
- **准备好发布？** → `/launch-checklist`

---

## 协作协议

此skill遵循协作设计原则：

1. **首先扫描**: 检查所有产物和质量门
2. **询问未知**: 不要假设你无法验证的事项通过
3. **呈现发现**: 显示带有状态的完整检查清单
4. **用户决定**: 裁决是建议——用户做出最终决定
5. **获取批准**: "我可以将此门检查报告写入 production/gate-checks/ 吗？"

**绝不**阻止用户推进——裁决是建议性的。记录风险
并让用户决定是否尽管有关注也要继续。
