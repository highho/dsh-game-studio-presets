# 引导式入职

此skill是新用户的入口点。它不假设您有游戏
想法、引擎偏好或任何先前经验。它先询问，然后路由
您到正确的工作流。

---

## 工作流

### 1. 检测项目状态（静默）

在询问任何内容之前，静默收集上下文以便您可以定制指导。
不要未经提示就显示这些结果——它们告知您的推荐，不是
对话开场白。

检查：
- **引擎已配置？** 读取 `.claude/docs/technical-preferences.md`。如果
  引擎字段包含 `[TO BE CONFIGURED]`，则引擎未设置。
- **游戏概念存在？** 检查 `design/gdd/game-concept.md`。
- **源代码存在？** 在 `src/` 中查找源文件（`*.gd`, `*.cs`,
  `*.cpp`, `*.h`, `*.rs`, `*.py`, `*.js`, `*.ts`）。
- **原型存在？** 检查 `prototypes/` 中的子目录。
- **设计文档存在？** 统计 `design/gdd/` 中的markdown文件。
- **生产产物？** 检查 `production/sprints/` 或
  `production/milestones/` 中的文件。

在内部存储这些发现。您将使用它们来验证用户的
自我评估并定制后续推荐。

---

### 2. 询问用户在哪里

这是用户首先看到的。清晰呈现这4个选项：

> **欢迎来到Claude Code Game Studios！**
>
> 在我建议任何内容之前，我想了解您从哪里开始。
> 您现在对游戏想法处于什么阶段？
>
> **A) 还没有想法** — 我根本没有游戏概念。我想探索
> 并弄清楚要做什么。
>
> **B) 模糊的想法** — 我心中有一个大致的主题、感觉或类型
> （例如，"与太空有关的东西"或"舒适的农场游戏"）但没有具体的内容。
>
> **C) 清晰的概念** — 我知道核心想法——类型、基本机制、也许
> 一个推介句子——但还没有将其正式化为文档。
>
> **D) 现有工作** — 我已经有设计文档、原型、代码或
n> 大量规划完成。我想组织或继续这项工作。

等待用户的回答。在他们回应之前不要继续。

---

### 3. 基于答案路由

#### 如果是A：还没有想法

用户需要在其他任何事情之前进行创意探索。引擎选择、
技术设置——所有这些都稍后进行。

1. 承认从零开始完全可以
2. 简要解释 `/brainstorm` 的作用（使用专业
   框架的引导式构思——MDA、玩家心理、动词优先设计）
3. 推荐下一步运行 `/brainstorm open`
4. 显示推荐路径：
   - `/brainstorm` — 发现您的游戏概念
   - `/setup-engine` — 配置引擎（头脑风暴会推荐一个）
   - `/map-systems` — 将概念分解为系统并规划GDD编写顺序
   - `/prototype` — 测试核心机制
   - `/sprint-plan` — 规划第一个冲刺

#### 如果是B：模糊的想法

用户有一颗种子但需要帮助将其成长为概念。

1. 请他们分享模糊的想法——即使几个字也足够
2. 将想法验证为起点（不要评判或重定向）
3. 推荐运行 `/brainstorm [他们的提示]` 来发展它
4. 显示推荐路径：
   - `/brainstorm [提示]` — 将想法发展为完整概念
   - `/setup-engine` — 配置引擎
   - `/map-systems` — 将概念分解为系统并规划GDD编写顺序
   - `/prototype` — 测试核心机制
   - `/sprint-plan` — 规划第一个冲刺

#### 如果是C：清晰的概念

用户知道他们想要做什么但还没有记录。

1. 问2-3个后续问题以了解他们的概念：
   - 类型和核心机制是什么？（一句话）
   - 他们有引擎偏好，还是需要帮助选择？
   - 大致范围是什么？（游戏jam、小项目、大项目）
2. 基于他们的答案，提供两条路径：
   - **先正式化**：运行 `/brainstorm` 将概念结构化到
     带有支柱、MDA分析和范围层级的适当游戏概念文档
   - **跳到引擎设置**：如果他们对概念有信心，直接
     转到 `/setup-engine` 然后手动编写GDD
3. 显示推荐路径（适应他们的选择）：
   - `/brainstorm` 或 `/setup-engine`（他们选择）
   - `/design-review` — 验证概念文档
   - `/map-systems` — 将概念分解为具有依赖关系和优先级的单个系统
   - `/design-system` — 编写每系统GDD（引导，逐节）
   - `/architecture-decision` — 做出第一个技术决策
   - `/sprint-plan` — 规划第一个冲刺

#### 如果是D：现有工作

用户已经有产物。弄清楚什么存在和什么缺失。

1. 分享您在第1步发现的（现在相关）：
   - "我可以看到您有 [X 源文件 / Y 设计文档 / Z 原型]..."
   - "您的引擎是 [配置为 X / 尚未配置]..."
2. 推荐运行 `/project-stage-detect` 进行全面分析
3. 如果引擎未配置，注意 `/setup-engine` 应该先来
4. 显示推荐路径：
   - `/project-stage-detect` — 全面差距分析
   - `/setup-engine` — 如果未配置
   - `/design-system` — 如果系统索引存在但GDD不完整
   - `/gate-check` — 验证下一阶段的准备情况
   - `/sprint-plan` — 组织工作

---

### 4. 继续前确认

呈现推荐路径后，询问用户他们想先采取哪一步。绝不自动运行下一个skill。

> "您想从 [推荐的第一步] 开始，还是您更愿意
> 先做其他事情？"

---

### 5. 移交

当用户选择他们的下一步时，让他们自己调用skill
或主动为他们运行。无论哪种方式，一旦用户有明确的下一步行动，`/start` skill的工作就完成了。

---

## 边缘情况

- **用户选择D但项目为空**：温和地重定向——"看起来
  项目是带有产物的全新模板。路径A或B会是
  更好的选择吗？"
- **用户选择A但项目有代码**：提及您发现的——"我注意到
  `src/` 中已经有代码。您是想选择D（现有工作）吗？或者
  您想用新概念重新开始？"
- **用户是回归（引擎已配置，概念存在）**：完全跳过入职
  ——"看起来您已经设置好了！您的引擎是 [X] 并且您
  在 `design/gdd/game-concept.md` 有游戏概念。想从上次离开的地方继续吗？
  尝试 `/sprint-plan` 或告诉我您想做什么。"
- **用户不适合任何选项**：让他们用自己的话描述他们的情况
  并适应。4个选项是起点，不是监狱。

---

## 协作协议

此skill遵循协作设计原则：

1. **先询问** — 绝不假设用户的状态或意图
2. **呈现选项** — 给出清晰路径，不是命令
3. **用户决定** — 他们选择方向
4. **不自动执行** — 推荐下一个skill，不要未经询问就运行
5. **适应** — 如果用户的情况不符合模板，倾听并调整
