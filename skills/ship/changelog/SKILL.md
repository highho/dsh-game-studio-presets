当此skill被调用时：

1. **读取参数**获取目标版本或冲刺编号。如果给定版本，
   使用相应的git标签。如果给定冲刺编号，使用冲刺日期范围。

1b. **检查git可用性** —— 验证仓库是否已初始化：
   - 运行`git rev-parse --is-inside-work-tree`确认git可用
   - 如果不是git仓库，通知用户并优雅中止

2. **读取git日志**自上次标签或发布以来：
   ```
   git log --oneline [last-tag]..HEAD
   ```
   如果没有标签存在，读取完整日志或合理的最近范围（最后100
   次提交）。

3. **从`production/sprints/`读取冲刺报告**，获取相关时期的
   计划工作背景和更改背后的上下文。

4. **从`design/gdd/`读取已完成的设计文档**，获取此期间
   实现的任何新功能。

5. **将每个更改分类**到以下类别之一：
   - **新功能**: 全新的游戏系统、模式或内容
   - **改进**: 现有功能的增强、UX改进、
     性能提升
   - **错误修复**: 对错误行为的纠正
   - **平衡更改**: 游戏数值、难度、经济的调整
   - **已知问题**: 团队知道但尚未解决的问题

6. **生成内部变更日志**（完整技术细节）：

```markdown
# 内部变更日志: [版本]
日期: [日期]
冲刺: [涵盖的冲刺编号]
提交: [数量] ([first-hash]..[last-hash])

## 新功能
- [功能名称] -- [技术描述、受影响的系统]
  - 提交: [hash1], [hash2]
  - 负责人: [实现者]
  - 设计文档: [链接（如适用）]

## 改进
- [改进] -- [技术上更改了什么及原因]
  - 提交: [hashes]
  - 负责人: [谁]

## 错误修复
- [BUG-ID] [错误描述和根本原因]
  - 修复: [更改了什么]
  - 提交: [hashes]
  - 负责人: [谁]

## 平衡更改
- [调整了什么] -- [旧值 -> 新值] -- [设计意图]
  - 负责人: [谁]

## 技术债务 / 重构
- [清理了什么及原因]
  - 提交: [hashes]

## 已知问题
- [问题描述] -- [严重性] -- [修复预计时间（如已知）]

## 指标
- 总提交数: [N]
- 更改的文件: [N]
- 添加的行数: [N]
- 删除的行数: [N]
```

7. **生成面向玩家的变更日志**（友好、非技术）：

```markdown
# [版本] 新内容

## 新功能
- **[功能名称]**: [玩家友好的描述，说明他们现在可以做什么
  以及为什么令人兴奋。关注体验，而非实现。]

## 改进
- **[什么改进了]**: [这如何让游戏对玩家更好。
  具体但避免术语。]

## 错误修复
- 修复了[描述玩家体验的问题，而非代码中的
  错误]
- 修复了[玩家可见的症状]

## 平衡更改
- [玩家易懂术语中的更改及设计意图。
  示例: "治疗药水现在恢复50 HP（从30上调）-- 我们感觉
  玩家需要在后期游戏遭遇中有更多恢复选项。"]

## 已知问题
- 我们知道[玩家术语中的问题描述]并正在努力
  修复。[如有解决方法。]

---
感谢您的游玩！您的反馈帮助我们让游戏更好。
在[链接]报告问题。
```

8. **向用户输出两个变更日志**。内部变更日志是
   主要工作文档。面向玩家的变更日志在审查后准备好
   发布到社区。

### 指南

- 绝不在面向玩家的变更日志中暴露内部代码引用、文件路径或开发者名称
- 将相关更改分组，而非列出单个提交
- 如果提交消息不清楚，检查相关文件和冲刺数据
  获取上下文
- 平衡更改应始终包括设计理由，而非仅数字
- 已知问题应诚实 -- 玩家欣赏透明度
- 如果git历史混乱（合并提交、还原、修复提交），清理
  叙述而非逐字列出每个提交
